# Резервное копирование MongoDB

## Где работает

- Единственный действующий стенд — локальный Compose. В неиспользуемом `docker-compose-cloud.yml` сервис `backup` настроен делать копию при старте и далее раз в `BACKUP_INTERVAL` секунд (по умолчанию 86400). При его будущем запуске в `backups_data` останутся последние `KEEP_LAST_N` архивов (по умолчанию 14).
- В локальном `docker-compose.yml` сервиса `backup` нет. Перед локальными операциями с БД делайте отдельную копию.
- Образ из `backup/Dockerfile` содержит MongoDB Database Tools и закреплён на `mongo:8.0.32`. Его `mongodump` проверен на MongoDB 6.0.26 и 8.0.32.

## Формат и границы копии

`backup/backup.sh` создаёт `humorpedia_backup_YYYYMMDD_HHMMSS.tar.gz`: внутри каталог с BSON-файлами базы `humorpedia` и метаданными индексов. Это копия **только указанной базы**. Пользователи базы `admin`, загруженные медиафайлы и другие Docker volumes в неё не входят.

Для обновления standalone MongoDB сначала остановите пишущие в базу сервисы, затем сделайте свежую копию и проверьте восстановление в отдельной базе/томе. `mongodump` при продолжающихся записях не даёт согласованного снимка всех коллекций. Дополнительно сохраните холодную копию остановленного `mongo_data`: она нужна для точного отката версии сервера и FCV.

## Создать копию при использовании cloud-шаблона

После остановки пишущих сервисов:

```bash
docker compose -f docker-compose-cloud.yml run --rm --no-deps -e BACKUP_INTERVAL=0 backup
```

Проверьте имя и размер нового архива в `backups_data`, затем распакуйте и восстановите его **в отдельном окружении**. Наличие файла само по себе не подтверждает возможность восстановления.

Процедура восстановления и ограничение `--drop` описаны в [RESTORE_BACKUP.md](RESTORE_BACKUP.md). Прямой архив `mongodump --archive --gzip` с расширением `.archive.gz` — другой формат; скрипты для `*.tar.gz` к нему не применяются.
