# Редакционное исследование комиков: проект механизма

Обновлено: 2026-09-25, Europe/Moscow. Ветка: `codex/editorial-research`, базовый HEAD `7eaf309`; в рабочем каталоге есть незавершённые изменения других задач, этот документ их не затрагивает.
Статус: первая ручная версия реализована; 9 исследовательских карточек загружены в локальную очередь, решения редактора ожидаются.

## Согласованный сценарий

- Поиск запускается вручную. На первом этапе исследование проводит Codex по запросу владельца, а админка хранит и рассматривает результаты. Кнопка в админке сама по себе не может запустить эту сессию Codex; для такого запуска впоследствии потребуется интеграция с отдельным поисковым и ИИ-сервисом.
- Первичный список новых комиков составляет Codex; владелец может добавлять имена.
- Сведения о личной жизни допускаются лишь при публичном подтверждении самим человеком либо надёжным интервью или редакционной публикацией. Для каждого такого утверждения обязательна прямая ссылка на источник. Слухи и выводы по косвенным признакам не предлагаются.
- Администратор или редактор утверждает, редактирует перед утверждением либо отклоняет каждое изменение. Публикация без решения человека не выполняется.

## Проверенные ограничения текущего проекта

- `correction_suggestions` и `/admin/correction-suggestions` служат для свободного текста читателей. Статус `fixed` только отмечает обработку: содержимое сайта эта очередь не меняет. Для структурированных исследовательских изменений нужна отдельная коллекция и экран или отдельная вкладка с собственным API.
- `people` хранит факты и биографию в разных местах: `bio`, `facts`, `facts_order`, `modules` (`text_block` «Биография», «Личная жизнь», `timeline`), а также связи. Исследовательское предложение должно указывать точное поле/модуль и показывать текущий и новый текст.
- `draft` виден публично наравне с `published`; скрывается `archived`. Поэтому анкету нового кандидата до утверждения нельзя заранее создавать в `people` как `draft`.
- Участия в шоу публично берутся из `show_appearances`, а не только из `Person.show_ids`. Текущая синхронизация удаляет исчезнувшие автоматические записи с `source=local_content`, поэтому утверждённое внешнее участие следует хранить как ручную запись с собственным источником и не перезаписывать синхронизацией.
- Для разрешения личностей уже есть `PersonLookup`: slug, имя и aliases, при неоднозначном имени связь не ставится автоматически. Использовать его для первого поиска дублей, затем требовать подтверждение редактора.

## Две ветки одного редакционного процесса

1. **Существующая страница.** Поиск по имени/псевдонимам и связанным шоу → извлечение отдельных утверждений → проверка дат и источников → сравнение с текущим документом и `show_appearances` → предложение только отсутствующих или противоречащих фактов. Совпадающие факты отмечаются как уже учтённые и в очередь не попадают.
2. **Новый человек.** Составить список по программам шоу, официальным страницам клубов и собственным страницам артистов → проверить совпадения по имени, алиасам и slug → сохранить карточку кандидата вне `people` → собрать подтверждённые поля и источники → дать редактору изменить анкету → по утверждению создать человека через существующий CRUD и связать проверенные участия. Созданную страницу можно далее открыть в обычном редакторе.

В обеих ветках результат поиска состоит из независимых фактов. Например, «участвовал в шоу» — отдельное структурированное изменение; обновление биографии — конкретный абзац `text_block`, а не замена всего HTML; дата рождения и личная жизнь — отдельные решения.

## Данные и экран админки

Новая коллекция `editorial_proposals` с типом `update_person` или `new_person`. Одна карточка содержит целевой `person_id` либо имя кандидата, статус (`new`, `in_review`, `accepted`, `rejected`, `conflict`), автора/время поиска, краткую причину и список изменений. Каждое изменение хранит путь к полю или ID модуля, старое значение и его версию, предлагаемый текст/структуру, выбранные источники и решение редактора. Источник хранит URL, название, дату публикации при наличии, время проверки и короткое место в материале, подтверждающее факт. Длинные заимствованные тексты и изображения не копируются.

Экран «Редакционные находки» показывает вкладки «Обновления» и «Новые люди», фильтры статуса, сравнение «сейчас → предлагается», источники рядом с каждым фактом и действия для каждого изменения: «Принять», «Изменить и принять», «Отклонить». Редактор может принять часть карточки. Для нового человека он видит похожие страницы в каталоге, редактирует название, полное имя и slug, затем решает, создавать ли страницу. Если найден тот же человек, кандидат отклоняется; перенос его фактов в карточку обновления пока выполняется отдельным исследовательским предложением.

Применение на сервере проверяет роль editor/admin, наличие и состояние целевой страницы, повторно сверяет её версию и не позволяет повторно применить одно решение. Если редактор изменил страницу после исследования, карточка становится конфликтной и требует нового сравнения. Принятые изменения проходят существующую валидацию полей и запись аудита: кто, когда, старое и итоговое значение, источники. Утверждённые участия в шоу сохраняются отдельными ручными записями, не затрагивая локальную синхронизацию. Для новой страницы проверяются уникальность slug и отсутствие дубля непосредственно перед созданием.

## Источники и качество

Приоритет: официальная страница шоу/клуба или артиста; затем интервью с прямой речью и редакционные материалы с названным автором и датой. Поисковый фрагмент, афиша с меняющимся составом и одиночное упоминание в выпуске служат поводом для проверки, а не готовой биографией. Важные даты и роли сверяются по первичному источнику. «Победитель выпуска» не превращается в «победителя шоу». Фото добавляется лишь после отдельной проверки права использования.

## Этапы реализации и проверка

1. Модели предложений, индексы и защищённый API для создания исследовательских карточек, редактирования решений и применения. Проверить права, валидацию, повторное применение, конфликт версии и отдельное хранение нового человека.
2. Экран админки с редактируемым сравнением и источниками. Проверить путь принятия части изменений, отклонение, создание новой страницы и ручное исправление.
3. Первый ручной исследовательский пакет: загрузить несколько обновлений и новых кандидатов, сверить с локальным каталогом и открыть в живой админке. Проверить изменённую публичную страницу и `docker compose ps` после утверждения тестового предложения.

До появления поиска внутри сайта владелец запускает исследование запросом Codex; защищённый импорт карточек не должен требовать передачи пароля администратора агенту.

## Реализация и проверка 2026-09-25

- Защищённый API `/api/editorial-proposals` хранит структурированные изменения и источники отдельно от публичных предложений исправлений. Решения применяются по фактам: принять, принять изменённое значение или отклонить. Повторный импорт одинакового пакета не создаёт дублей. При изменении исходного поля предложение получает конфликт вместо перезаписи.
- Экран `/admin/editorial-proposals` показывает обе ветки, фильтры статуса, старое и предлагаемое значение, источники, поиск похожих людей, редактирование и решения. JSON можно выбрать файлом либо вставить текстом; импорт разрешён редактору и администратору.
