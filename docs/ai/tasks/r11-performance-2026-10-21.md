## Изменения и границы

Основание — [R11 общего плана](project-refactoring-plan-2026-10-21.md). Схема и результаты API, видимость и CAS сохранены.

- `find_adjacent_seasons` сохраняет приоритет индексируемых metadata → legacy → parent map → final regex. Полный legacy-ответ менее 20 строк без соответствующего фрагмента пути доказывает пустоту последних regex. Parent map проверяется прежде пропуска. При 20 строках, missing/non-string path или подходящем фрагменте старый fallback остаётся. OR-объединение не вводилось, чтобы не менять выбор дублей.
- `create_competition_indexes` добавляет шесть отдельных multikey-индексов: `team_id` и `slug` в `teams`, `winners`, `stages.games.results`. Индексируются все ветви существующего OR, читаются только связанные канонические сезоны.
- `create_recommendation_indexes` добавляет в `people/teams/shows/kvn` индекс `featured DESC, views DESC, published_at DESC, _id ASC` с прежним порядком сортировки. Индекс с ведущим `show_id` не добавлен: мог бы менять ограниченный неупорядоченный relevance pool. Малые коллекции без измеренной необходимости не индексируются.
- [profile_api.py](../../../backend/scripts/profile_api.py) измеряет реальные GET через `server.app` на копии, требует пользователя с единственной ролью `read` своей `humorpedia_perf_<32hex>` базы. Проверяет DB, роли, whitelist маршрутов и HTTP 200. Без lifespan не создаёт индексы/админов и не запускает flush просмотров.
- Основной checkout/стек остаётся на `main ca46155`. Импорт 24СМИ не изменялся; записей в общую Mongo и действий на VPS не было. Новые индексы созданы только на одноразовой копии. Их стоимость для записи и длительность построения ещё не измерены.

## Метод

Собственная MongoDB 8.0.32, сеть и временные тома без опубликованных портов. Скопированы 16 коллекций / 31 571 документ с исходными индексами: people, teams, shows, kvn, seasons, tournaments, participations, memberships, show_appearances, articles, news, quizzes, cities, sections, tags, site_settings (только recommendations/related_news). Нет users, импортных/редакционных очередей и секретной конфигурации. Копия последовательная, не транзакционный snapshot живого источника. Counts и SHA256 канонического BSON совпали после копирования и всех замеров.

Контроль: четыре production-файла из `7ad0577` во временном каталоге отдельного контейнера, новые десять индексов отсутствуют. После: текущий код worktree и эти десять индексов в той же копии. Git checkout не переключался. Профилировщик и план одинаковые.

Исходная диагностическая пара 21.10: 100 cold + 100 warm на десять сценариев, суммарно 4000 измеренных GET и отдельные прогревы. Cold очищает только кэш приложения, не OS/WiredTiger. `--without-rate-limit` явно включён в обоих частных ASGI-процессах для серии больше 60/min в поиске; работающий стенд не менялся, limiter восстанавливается при выходе/ошибке.

Explain после timed samples: 110 уникальных запросов до и 104 после, ошибок нет. Статистика полного запроса не учитывает клиентский `to_list(n)`. `aggregate_cursor.n_returned` — вход pipeline, не финальный API-ответ. `getMore` учитывается отдельно от логических find/aggregate/count/distinct.

Raw response SHA256 и content SHA256 разделены. Только у kvn/by-path из content SHA исключён корневой `/team_data_version`, создававшийся через datetime.now при cache miss и до R11. Порядок массивов, прочие timestamps и вложенные поля участвуют в сравнении. Все 20 сочетаний сценарий/режим совпали между версиями и стабильны внутри серии.

## Продолжение диагностики p95

Проверка с GC callbacks (`.cache/r11/diagnose-before.json`): пять крайних хвостов season-edge
cold совпали с gen2 GC паузами 38,71–53,50 мс; один search cold — 46,76 мс. Это прямое
объяснение отдельных всплесков, но не всех p95. Search cold в этой серии имеет p95 38,03 мс
при GC около 0,16 мс на пограничном sample: сводить всё ухудшение к GC неверно.

В прежний timed interval также входили deepcopy Mongo-команд в CommandListener и HTTPX
INFO-запись клиентского журнала на bind mount. Агрегирование/hash выполнялись после таймера,
но их аллокации могли влиять на последующий GC в общем процессе.

Добавлен `--timing-only`: listener не создаётся/не регистрируется; Mongo metrics=null, explain
пуст, HTTPX INFO выключен только внутри CLI с восстановлением. GC включён. Samples получили
timestamps. Счётчики/explain измеряются отдельно. Прежние отчёты сохранены как исторические.

Протокол до выполнения: `.cache/r11/acceptance-protocol.json`, AB BA AB BA AB, пять блоков
на версию × 100 cold/warm на каждый из десяти маршрутов, суммарно 20 000 GET. Fresh process
на блок, та же копия с исходными индексами против десяти R11 индексов. Affinity: profiler
28–29, Mongo 30–31 из 32 виртуальных CPU; это не резервирует физический хост. Выбросы и серии
не исключаются; pooled nearest-rank p95 по всем равным samples каждого маршрута/режима.

Полный путь timing-only проверен при успешном output и IsADirectoryError. Оба теста сначала
воспроизвели безусловный listener.pause(), затем **15 passed** после исправления. Проверяются
close_db и восстановление limiter/logger/DB_NAME. Неуспешный первый блок сохранён как
invalid-teardown-* и в приёмку не входит.
