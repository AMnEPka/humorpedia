# Локальный конструктор страниц и перенос на прод: план реализации

Дата: 05.10.2026, Europe/Moscow. Основание: `main`, HEAD `1813cf02f08c9aa202e01167c2d3eb6886ab753c`.
Статус: проект решения и план; реализация не начата. Согласованы запуск кнопкой через локальный Codex CLI и работа с неполными фактами по решению редактора. Остальные решения ниже — предлагаемый объём реализации.

## 1. Результат и границы

В локальной админке появляется «Конструктор страниц». Владелец выбирает человека, команду КВН или шоу, добавляет фото, известные факты, достижения, ссылки и свободные заметки. Нажатие «Собрать страницу» запускает установленный на Windows Codex CLI под учётной записью владельца. Он предлагает связный текст и структуру стандартной страницы Humorpedia. Редактор видит результат, исправляет его, проверяет внешний вид и скачивает один переносимый файл. Админка прода принимает этот файл, показывает проверку и предпросмотр, а после отдельного решения создаёт страницу.

Критерий готовности: подготовленная локально страница переносится вместе с изображениями и выбранными ручными связями в другую базу с другими ID, выглядит тем же образом и дальше редактируется штатной админкой. До решения о публикации её нет в публичных страницах, поиске и связанных блоках.

Согласованные ограничения:

- Генерация — по кнопке через **локальный Codex CLI**, без интеграции сайта с OpenAI API по отдельному ключу.
- Источник содержания — переданные владельцем сведения. Автоматический поиск людей и веб-исследование не входят в первый выпуск. Переданная ссылка сама по себе не означает, что содержимое сайта было прочитано и проверено.
- Неизвестные сведения остаются неизвестными. Отсутствие даты/города рождения или двух шоу даёт предупреждение, а не запрет создать страницу по решению владельца.
- Перенос на прод — вручную через файл и админку. Локальному конструктору не нужны адрес API и учётные данные прода.

Предлагаемый первый выпуск: создание **новых** страниц трёх типов. Человек со специализацией «стендап-комик» — существующая сущность `person`, а не новый тип коллекции. Для команд сначала поддерживается КВН; для шоу — самостоятельная страница. Вложенные шоу, команды конкретных шоу, обновление существующей страницы пакетами и массовый импорт — следующие расширения того же формата. При встрече такого объекта первая версия явно сообщает о неподдерживаемом варианте.

Конструктор собирает содержание и модули по существующему дизайну Humorpedia. Он не генерирует произвольную вёрстку, JavaScript или новый дизайн для каждого человека.

## 3. Пользовательский сценарий

1. **Новая заготовка.** Тип сущности, публичное имя/название, специализация, фото/логотип/постер. Для человека — дата и место рождения, для команды — город и год основания, для шоу — формат и дата старта. Все дополнительные сведения необязательны на этапе ввода.
2. **Материалы.** Структурированные факты и одно большое поле «Что известно»: тезисы, события, достижения, роли, участники. Ссылки, источник фото и подпись можно добавить рядом. Материалы автоматически сохраняются; после перезагрузки ввод восстанавливается.
3. **Собрать страницу.** Показать состояния «В очереди», «Составляется», «Готово», «Ошибка», возможность отмены. При недоступном исполнителе исходные материалы остаются сохранёнными.
4. **Проверить.** Рядом исходные факты и результат: введение, биография/история, карьера, достижения, хронология и факты. Показывать, какие сведения использованы, какие противоречат друг другу и чего не хватает. Пустые разделы не добавлять ради объёма.
5. **Отредактировать.** Править поля и модули штатными компонентами. Повторная генерация создаёт новую версию предложения; изменения редактора принимаются/заменяются явно через сравнение. Никакого безусловного затирания.
6. **Предпросмотр.** Увидеть страницу с действующим публичным оформлением, фото, боковой колонкой и модулями, включая мобильную ширину. Пробелы в фактах обсуждаются в редакторе, а не попадают служебными предупреждениями в статью.
7. **Экспорт.** «Скачать страницу» формирует `имя.humorpedia.zip`. Технические ошибки блокируют экспорт; редакционные предупреждения можно подтвердить с сохранением решения.
8. **На проде.** «Импорт страницы» → выбрать ZIP → проверить страницу, фото, совпадения и связи → «Создать и опубликовать». До последнего шага публичный контент не изменяется. Результат показывает публичный URL и ссылку на обычный редактор.

Создавать полноценный публичный документ в локальной базе ради предпросмотра не требуется. Проверка и экспорт работают непосредственно с заготовкой.

## 4. Работа с фактами и текстом

Хранить раздельно:

- `source_materials`: введённые сведения и файлы, стабильные ID отдельных фактов, происхождение (`user_provided`, URL/название источника при наличии).
- `generated_versions`: предложения Codex с ревизией входа, версией шаблона задания, выбранной моделью, временем и перечнем использованных фактов.
- `edited_page`: текущая редакторская версия полей, модулей и связей; номер ревизии и отметка проверки.

Codex получает задачу литературно переработать и упорядочить сведения: нейтральный энциклопедический стиль, без рекламных эпитетов, домыслов, расширения дат и добавления достижений «из памяти». Переданные материалы — данные, а не команды для исполнителя. Противоречие «1988»/«1989» возвращается вопросом редактору. Фото не используется для определения личности или выведения биографических фактов.

Предложение возвращается по JSON Schema: `page`, `relations`, `fact_usage`, `warnings`, `questions`. Сервер повторно валидирует структуру, типы модулей, ссылки и соответствие фактов источникам. Наличие JSON Schema не доказывает правдивость текста: финальная редакторская проверка обязательна.

Проверки делятся на:

- **Ошибки:** нет имени/названия, неподдерживаемый тип, некорректная дата при её указании, повреждённое изображение, неизвестный модуль, запрещённый HTML/URL, противоречие обязательных технических полей.
- **Предупреждения:** неизвестна дата/город, мало материала для биографии, нет фото, нет ссылки на источник, неполный состав команды. Редактор может продолжить; система не придумывает дополнения.

Частичная дата сохраняет исходную точность. Год не дополняется вымышленными днём/месяцем, день и месяц — вымышленным годом. Для человека адаптер согласованно заполняет `bio` и отображаемые `facts/facts_order`: сейчас публичная страница читает оба представления, поэтому дата не должна расходиться между ними.

Политика конструктора не меняет автоматически действующие проверки старой очереди исследовательских предложений. Это отдельный способ подготовки материала с явным решением владельца.

## 5. Локальный исполнитель Codex

Рекомендуется **отдельный Windows-процесс с вызовом `codex exec`**. Вариант с ручным переносом задания в чат требует больше действий пользователя; `codex app-server` полезен для сложного интерактивного клиента, но для одной операции «вход → структурированный результат» добавляет ненужный протокол и жизненный цикл.

Связь backend и исполнителя — файловая очередь в отдельной папке `var/page-builder`, смонтированной в dev-контейнер. Исполнитель не открывает HTTP-порт, не получает доступ к MongoDB и не хранит пароли админки. Redis/Celery не нужны для одного редактора и одной параллельной генерации.

Последовательность:

1. Защищённый локальный API сохраняет заготовку и готовит неизменяемый снимок входа: `job_id`, `draft_id`, ревизия, hash, материалы и схема. Файл задания публикуется атомарным переименованием после полной записи.
2. Исполнитель на Windows забирает задание с блокировкой, отмечает время/heartbeat и вызывает Codex из рабочего каталога задания, а не из корня репозитория.
3. Задание передаётся через stdin; пути и аргументы формируются кодом. Пользовательский текст не включается в исполняемую shell-строку.
4. CLI использует сохранённую авторизацию ChatGPT. Сайт не вызывает OpenAI API сам; учётные данные Codex остаются на Windows, не монтируются в контейнер и не входят в пакет.
5. Вывод ограничивается схемой; JSONL используется для статуса, финальный JSON записывается отдельно. Исполнитель не применяет результат к странице и не выполняет команды из ответа модели.
6. Backend принимает только валидный завершённый результат для известного задания. Если ревизия ввода уже изменилась, результат помечается устаревшим и не заменяет текущую редакцию.

Исполнитель стартует отдельным скриптом `scripts/start-page-builder.ps1`, без видимого вспомогательного окна. Он не зависит от текущего чата Codex; на странице есть индикатор доступности. Исходные материалы остаются доступны, даже когда исполнитель остановлен.

Границы запуска:

- Возможность включается явно через `LOCAL_PAGE_BUILDER_ENABLED`; при `ENVIRONMENT=production` API генерации не регистрируется даже при ошибочно установленном флаге.
- Локальные порты фронтенда/backend привязываются к loopback в конфигурации стенда, на котором включён исполнитель. Проверка прав — через `require_editor`, а не через скрытие кнопки.
- Контролируемый профиль Codex: минимальные разрешения, без подключения проектных MCP, внешних интеграций и поиска. `read-only` сам по себе не гарантирует ограничения чтения только папкой задания: конкретный профиль и доступ к файлам нужно подтвердить первым техническим испытанием.
- Вызывать CLI без отключения sandbox и без автоматического повышения прав. Не передавать в процесс переменные с паролями MongoDB, JWT или доступами прода.
- Один активный запуск; тайм-аут и отмена завершают дерево процесса. После перезапуска зависшие задания становятся прерванными; новый запуск — явное действие, без бесконечных повторов и повторного расхода лимита.
- Фото обязательно сохраняется для страницы, но отправлять его модели для простого составления биографии не требуется. Подпись и alt можно составить из имени; поддержка `--image` оставляется для явно необходимой обработки изображения.

**Локальный Codex не означает офлайн-модель.** Генерация обращается к сервису Codex, требует интернета и расходует доступные лимиты аккаунта. Вход через ChatGPT и использование сохранённой авторизации в `exec` описаны в [официальной документации об авторизации](https://learn.chatgpt.com/docs/auth) и [неинтерактивном режиме](https://learn.chatgpt.com/docs/non-interactive-mode). [Структурированный вывод](https://learn.chatgpt.com/docs/non-interactive-mode#create-structured-outputs-with-a-schema) подтверждает выбранный способ обмена.

## 6. Формат переноса страницы

Один ZIP с версионированным контрактом `humorpedia.page-package`, версия `1`:

```text
manifest.json       формат, версия, package_id, entity_key, ревизия, перечень файлов/hash
page.json           тип, поля страницы, модули, SEO, теги
relations.json      переносимые ручные связи и ссылки на сущности
editorial.json      происхождение фактов и решения редактора, без логов Codex
assets/             используемые фото, логотипы, изображения модулей
```

Правила контракта:

- `entity_key` — UUID заготовки, стабильный между экспортами. `package_id` — идентичность конкретного экспорта; повторное скачивание неизменной версии сохраняет её. Новый редакторский вариант получает новую ревизию и пакет.
- Пакет включает один основной объект. Автоматически затягивать весь граф связанных страниц нельзя: зависимости перечисляются и разрешаются на принимающей стороне.
- Исключить локальные `_id`, системные даты, пользователей, просмотры, рейтинги/голоса, комментарии, старые идентификаторы импорта и секреты. На проде появляются собственные ID и аудит.
- Фото и изображения модулей используют переносимые ссылки `asset:<id>`. Importer преобразует их в адреса целевого хранилища; в статье не остаётся `localhost`, дисковых путей и локальных `/uploads/...`.
- Изображения хранить файлами, не base64 внутри JSON. В manifest — MIME, размер, SHA-256, alt/подпись и источник при наличии. Ограничение одного изображения — 10 MiB, как у нынешнего media API; предложенный лимит ZIP — 50 MiB, распакованного содержимого — 100 MiB, до 100 файлов. Лимиты дублировать в UI и на сервере.
- Разрешить только поддерживаемые растровые изображения и проверять реальное декодирование/размеры, а не только расширение. Для первой версии не принимать HTML/SVG как медиа. Распаковка не допускает абсолютных путей, `..`, ссылок и повторяющихся имён.
- Внутренние ссылки представлять путями нового сайта или типизированными ссылками на сущность. Внешние URL остаются внешними ссылками; importer не скачивает их автоматически.
- Разрешать только утверждённое подмножество модулей из реестра. Системные модули — настройки вида. Генерируемые блоки игр, рекомендаций, новостей, рейтингов и статистики не копируются как статический результат.
- HTML текстовых модулей проходит серверный allowlist и очистку до сохранения/предпросмотра. Схема данных и права редактора не заменяют проверку разметки; генерация raw `html`-модулей исключена.

Переносимая ссылка содержит тип, slug и при необходимости полный путь/контекст. Например, для человека достаточно `person + slug`, для команды шоу нужны также шоу и путь. ID локальной базы не служит доказательством совпадения. Сопоставление только по имени всегда требует решения редактора.

В первой версии переносить следующие ручные связи:

- У человека — выбранные участия в существующих на проде шоу через `show_appearances`.
- У команды КВН — состав с именами, ролями и периодами через `memberships`; участник может остаться без ссылки на страницу человека.
- У шоу — вручную подготовленные карточки участников с разрешёнными ссылками; создание страниц участников не производится.

Не переносить автоматически `participations`, результаты сезонов и вычисленные достижения. Достижение, переданное текстом, остаётся редакционным текстом; появление его в турнирной статистике требует отдельного внесения структурированных результатов.

Обязательные неразрешённые ссылки блокируют применение; необязательную связь редактор может снять, сохранив текст без ссылки. Ничто не отбрасывается молча. Следующая версия сможет импортировать зависимости отдельными пакетами, начиная с родителей.

## 7. Импорт в админке прода

Отдельный экран `/admin/page-import` доступен `admin/editor`. Конструктор и исполнитель на проде отсутствуют; на прод поставляются контракт пакета, валидация, предпросмотр и импорт.

Двухэтапный API:

- `POST /api/page-packages/preview`: принять пакет в закрытое временное хранилище, проверить формат и файлы, показать страницу, коллизии и сопоставление связей. Возвращает `import_id`, hash и описание плана; публичные коллекции не изменяет.
- `POST /api/page-packages/{import_id}/apply`: принять решения о связях и точную проверенную ревизию. Повторно проверить права, hash, актуальность сопоставлений, конфликты slug/тегов. Применить только после явного действия редактора.
- `GET /api/page-packages/{import_id}`: состояние/результат для восстановления после обрыва связи. Закрытые изображения предпросмотра выдаются только авторизованному редактору.

Важные правила применения:

1. **Создание через доменный слой.** Использовать те же проверки и действия, что штатная админка. При необходимости вынести небольшие create-операции из хендлеров в переиспользуемые сервисы; не использовать произвольный Mongo import и не дублировать CRUD.
2. **Совпадения.** Если slug/путь занят или есть кандидат-дубль, ничего автоматически не заменять и не добавлять суффикс. Предложить проверить существующую страницу либо явно выбрать другую идентичность. Обновление существующего документа — отдельный этап развития.
3. **Повтор.** Журнал импорта с уникальным `package_id` и соответствием `entity_key → target_id` не позволяет создать дубликат при повторной загрузке, двойном нажатии или потерянном HTTP-ответе. Новая ревизия уже импортированной сущности в create-only версии сообщает, что нужен сценарий обновления.
4. **Файлы.** Сначала проверенные данные во временном хранилище, затем файлы в обычном media storage и remap всех ссылок. Повторное применение использует уже подготовленные файлы. Не удалять общие медиа при восстановлении неудачной операции.
5. **Составы и участия.** Записи получают детерминированный `_id` от `entity_key + relation_id` и создаются через upsert, используя уникальность `_id`; существующие поисковые индексы memberships сами по себе дублей не предотвращают. Составы сохраняются с `source=manual` и происхождением пакета. На пути пакетного создания команды отложить автоматический разбор roster-модулей до записи ручного состава, затем запустить штатное согласование, которое исключает ручные имена. Для show_appearances сопоставить `person_id`, `show_id`, при наличии `team_id`; `source_page_id` у ручного участия первой версии равен целевому ID выбранного шоу, как в действующей редакционной очереди. Использовать `source=editorial` с отдельными полями происхождения пакета: синхронизация удаляет устаревшие `local_content`, но должна сохранять ручной импорт. Перед применением сравнить уже существующее участие person/show и не создавать второй вариант без решения редактора.
6. **Частичные сбои.** Текущий проект использует standalone MongoDB; нельзя обещать общую транзакцию MongoDB и файловой системы. Нужен журнал шагов и повторяемые операции. Документ до завершения применения остаётся `archived`; привязки и побочные синхронизации выполняются с контролем состояния операции. Проверить, что незавершённые/архивные объекты не проявляются через списки связей. На ошибке — явное состояние восстановления, без сообщения «готово» и без удаления чужих изменений.
7. **Публикация.** После записи файлов, связей и повторной проверки установить `published`, сбросить кэш штатным механизмом, проверить `raw=true` и публичный URL. Зависимые синхронизации должны иметь явный этап завершения; сохранённый, но не полностью применённый пакет не объявляется успешно опубликованным.

Журнал хранит hash пакета, автора, целевой ID, сопоставления, шаги, ошибки и итог. Полные prompts, авторизация Codex и исходные секреты туда не попадают. Незавершённые загрузки можно удалить из очереди; публичный контент при этом не затрагивается.

## 8. Предпросмотр и модель хранения

Коллекции: `page_builder_drafts` для локальных материалов/редакторских версий и `page_package_imports` для журнала приёма. Состояние генерации отделить от редакторской готовности: завершённый процесс Codex ещё не означает утверждённую страницу. Обновления заготовки используют номер ревизии, чтобы две вкладки не перезаписывали друг друга.

Приватные вложения и очередь располагаются вне статических `/uploads` и `/media`. Редакторские входы читаются только через защищённые маршруты. Готовые изображения становятся обычным media-контентом при применении импорта.

Предпросмотр должен переиспользовать публичные представления `PersonDetailPage`, `TeamDetailPage`, `ShowDetailPage` с переданным документом и разрешёнными связями. Минимально отделить получение данных от отображения; не создавать вторую независимую вёрстку. Явный `preview`-режим передаёт данные через интерфейс только чтения и распространяется на вложенные компоненты: просмотры, ratings/comments/votes и прочие операции записи не вызываются; обращения к production URLs отсутствуют. Закрепить это проверкой сетевых вызовов при открытии и взаимодействии с preview. Динамические рекомендации/новости обозначать как блоки целевого сайта: на локальном и продовом наборе данных они закономерно могут отличаться.

## 10. Проверки и критерии приёмки

Целевые новые тесты: `backend/tests/test_page_builder.py`, `test_page_packages.py`, `test_page_package_import.py`, `scripts/page-builder/test_worker.py`, `frontend/src/admin/pages/PageBuilderPage.test.jsx`, `PageImportPage.test.jsx`. UI-тесты проверяют пользовательские действия и сохранение текста; испытания архива/прав/повторного применения — на сервере.

Особое внимание при ревью:

- Изменили ввод во время генерации: поздний ответ не затирает новую ревизию.
- Сеть оборвалась после записи: повтор apply возвращает прежний результат, а не второй документ.
- В локальной и целевой БД разные ID: ссылки, фото, состав и участия корректно сопоставлены.
- Пустые/неполные сведения и русские кавычки, тире, HTML: сохраняется смысл, не выдумываются данные, не исполняется разметка.
- Заготовка/пакет/незавершённый импорт не видны анонимно ни по прямому URL, ни через поиск, связанные списки или статические файлы.

Команды обязательной проверки после реализации:

```powershell
docker compose exec -T backend pytest -q tests
docker compose exec -T frontend yarn test --watchAll=false --runInBand
docker compose exec -T frontend yarn build
docker compose ps
powershell -ExecutionPolicy Bypass -File .\scripts\dev-status.ps1
```

Тесты исполнителя запускать отдельно установленным Python на Windows. После правок Compose/зависимостей выполнить полный `scripts/dev-sync.ps1`. Проверить релевантные экраны на `http://localhost:3000` и API на `http://localhost:8001`, включая неавторизованные запросы и изображения. Сравнивать поля/модули экспортируемой версии с `raw=true` после импорта, исключая ожидаемо новые ID, даты и адреса файлов.

Целевую БД для round-trip изолировать от общей `mongo_data` и от прода; не поднимать второй стандартный Compose-стек с теми же именами/портами. Production-gating проверять отдельным конфигурационным тестом и проверкой состава маршрутов. Реальную публикацию и её проверку выполнять только после отдельного решения о внедрении.
