# Задача: восстановление пропущенных модулей старого сайта

Обновлено: 2026-09-18 07:48 +03:00.
Область: MODX-дамп, модульная модель backend, публичные страницы и админка frontend, миграция пользовательских данных.
Основание: ветка `codex/module-contract`, HEAD до незакоммиченных изменений — `2bab47f17c7a27c45b0670b88e19c52ea001e2fa` (актуальный origin/main при старте).
Статус: этап 0 реализован; страницы сезонов закреплены как special без публичного рендера старых modules.

## Результат и границы

Цель — восстановить функциональные блоки опубликованного старого сайта, которые отсутствуют или работают не полностью
на новом Humorpedia. Источник истины для состава старых блоков — `backups/idemsku8_modx2.sql`; текущая реализация проверялась
по backend-моделям, импортёрам, публичному рендеру, админке и локальной MongoDB.

Не следует механически создавать новый модуль для каждого имени MIGX-формы: значительная часть форм была обвязкой MODX,
а не самостоятельным контентом. Критерий готовности всего этапа — каждый содержательный старый блок либо имеет проверенный
эквивалент, либо восстановлен, либо явно исключён по продуктовому решению.

## Полные и частичные пробелы

### 1. Рекомендации: `popular_articles` и `related_articles`

- `popular_articles`: 664 блока. Лимиты: один блок на 6 карточек, 240 на 2, 423 на 3.
- `related_articles`: 31 блок, везде заголовок «Читайте также», поле `articles` пусто.
- Значит, старый сайт подбирал материалы динамически; импортировать 695 одинаковых записей не нужно.
- В `Article` и `News` есть `related_article_ids`, но create/update-схемы, админка и публичные страницы не доводят связь
  до работающего результата. В текущей MongoDB нет статей или новостей с заполненным `related_article_ids`.

Рекомендация: один компонент рекомендаций с ручным приоритетом через `related_article_ids` и динамическим fallback по тегам,
типу контента, рейтингу и популярности. Текущую страницу всегда исключать.

### 2. Оглавление статей: `table_of_contents`

- 127 видимых маркеров: 80 страниц людей, 37 статей, 7 страниц команд «Импровизация. Команды» и 3 прочие страницы.
- На страницах людей `PersonDetailPage.jsx` уже строит оглавление по событиям timeline; на страницах команд
  `TeamDetailPage.jsx` — по заголовкам `text_block`. Их идентификаторы совпадают с реальными якорями контента.
- Корневая страница КВН имеет отдельное рабочее оглавление в `SectionDetailPage.jsx`.
- `ModuleRenderer.jsx` намеренно возвращает `null` для `table_of_contents`, потому что рабочие оглавления выводятся
  на уровне шаблона страницы. Сам по себе этот `null` не является дефектом.
- Непокрыты 37 старых статей с маркером оглавления: `ArticleDetailPage.jsx` отдельного оглавления не имеет.

Рекомендация: не менять хорошо работающие страницы людей и команд. Для статей добавить page-level оглавление по названиям
`text_block` и заголовкам `h2/h3`, переиспользовав правила уникальных якорей. Пустые MODX-маркеры не импортировать.

### 3. Опросы: `voting`

- 50 видимых блоков размещены на 18 страницах: 49 в новостях и 1 в статье.
- Блоки ссылаются на 50 определений опросов с TV `vote_answers`.
- В `modx_uservotes` находится 596 голосов 57 пользователей по 51 идентификатору опроса; есть осиротевшие или
  неполные ссылки, поэтому импорт обязан формировать предупреждения.
- Текущий сайт имеет право пользователя `vote` и счётчик `stats.votes_count`, но модели опроса, API и UI отсутствуют.

Рекомендация: коллекции `polls` и `poll_votes`, а в контенте — лёгкий модуль `poll` со ссылкой на опрос. Исторически
переносить агрегаты ответов, но не привязывать старые `user_id` к новым аккаунтам без отдельного решения по приватности.
Новые голоса по умолчанию принимать только от авторизованных пользователей, один голос на пользователя и опрос.

### 4. Комментарии

- Маркер комментариев стоял на 896 новостях и 42 статьях.
- Аудит импорта статей и новостей зафиксировал 195 комментариев к опубликованным статьям и 859 к опубликованным новостям,
  всего 1054; см. `articles-news-import.md` и `DATA_MODEL.md`.
- Backend `routes/comments.py`, модель и административная модерация существуют.
- Публичные страницы показывают только `comments_count`; списка, формы и ответов нет. В локальной MongoDB — 0 комментариев.
- Текущий API создаёт комментарии сразу одобренными и позволяет многократно увеличивать `likes`, поэтому перед открытием
  публичного UI его нужно усилить.

Рекомендация: сначала публичный блок для новых комментариев с авторизацией, премодерацией, пагинацией, ограниченной
вложенностью, rate limit и одной реакцией пользователя. Старые комментарии импортировать отдельным этапом после решения
об авторах, персональных данных и сохранении цепочек ответов.

### 5. Контакты

Старый блок содержит `marketing@humorpedia.ru`, `admin@humorpedia.ru` и `https://t.me/humorpedia_ru`. Текущая
`ContactsPage.jsx` показывает другие адреса и Telegram, а форма не отправляет сообщение — только выводит `alert`.

Рекомендация: восстановить проверенные контактные ссылки и убрать фиктивную форму до появления реального почтового или
тикетного backend. Старый сайт такой формы не требовал.

### 6. Функции вне системы страниц

- В TV `ranks` корневой страницы есть 9 пользовательских уровней: от «Незнакомца» до «Легенды» и служебного ранга
  «Главный редактор». В текущем сайте есть статистика действий, но нет баллов и рангов.
- TV `related` заполнен только у трёх ресурсов, и все три значения указывают на одного человека. Это похоже на ручной
  артефакт или ошибку копирования; автоматически переносить его нельзя.
- Ранги и рекламные блоки не являются обязательной частью восстановления контента. Их следует планировать только после
  отдельного продуктового решения.

## Технический блокер перед расширением

Исходное состояние до этапа 0 (устранено в текущей рабочей ветке, см. фактический статус ниже):

- backend `ModuleType` принимает `gallery` и `video`;
- публичный `ModuleRenderer` ожидает `image_gallery` и `video_embed`;
- renderer знает `person_card`, `related_links`, `html`, `divider`, которых нет в backend enum;
- часть типов, доступных в админке, редактируется только как JSON или не имеет общего публичного рендера;
- неизвестный тип может сохраниться или попасть в документ, а затем молча не отобразиться.

До добавления новых блоков нужен канонический реестр типов и контрактный тест: каждый тип обязан иметь backend-схему,
админ-редактор и публичный renderer либо быть явно помечен как системный или обрабатываемый специальной страницей.

## Открытые решения

- **Опросы:** рекомендовано импортировать исторические агрегаты без привязки к старым пользователям.
- **Комментарии:** выбрать анонимизацию старых авторов либо подтверждённое сопоставление аккаунтов; без решения импорт блокирован.
- **Модерация:** рекомендовано публиковать новые комментарии только после одобрения модератором.
- **Контактная форма:** рекомендовано удалить до появления реальной доставки.
- **Ранги и реклама:** по умолчанию не входят в ближайшие этапы.
